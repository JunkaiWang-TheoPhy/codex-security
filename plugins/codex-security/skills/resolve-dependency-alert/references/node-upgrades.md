# npm and pnpm dependency evidence

Locate the lockfile governing the reported manifest and the workspace importer that owns it. Record its digest and the project's declared package-manager version. Evaluate the checked-in graph before consulting a local installation, which may be stale. For read-only assessment inspect the lockfile as data, or run the pinned manager's graph command in a disposable copy without network or credentials. Repository package-manager hooks can execute code. Reserve installation and lifecycle scripts for authorized candidate verification with the project's existing isolation and registry controls.

| Manager | Read the resolved graph | Validate an approved candidate |
| --- | --- | --- |
| npm | From the lockfile root, use `npm ls --package-lock-only --all --json` and inspect each path to the affected package. Include the root and workspace packages. For lockfiles with a `packages` table, inspect nested install locations, actual names behind aliases, `resolved` and `integrity`. | Update the owning requirement with the project's npm version, regenerate its lockfile and run `npm ci` in the isolated candidate. Compare the graph and exercise affected callers. |
| pnpm | With a version supporting it, use `pnpm list --recursive --depth Infinity --lockfile-only --json` from the workspace root. Include the root importer if the workspace selection omits it. Follow importer references through snapshots, including peer-qualified variants, aliases and workspace links. | Update the owning workspace or a supported parent, regenerate `pnpm-lock.yaml` and perform a frozen install with the project's pnpm version. Compare all resolutions and peer requirements. |

If the installed manager lacks a lockfile-only option, inspect the lockfile's native structures and use an authorized clean frozen install for corroboration in standard verification. Keep missing or invalid graphs, skipped optional platforms, unresolved aliases and incomplete workspace coverage explicit. Never treat a failed command or an empty filtered listing as evidence of absence. In static mode read the graph as data and evaluate existing check evidence only.

Separate impacted copies from unaffected duplicates. For a transitive copy, identify the nearest supported parent that allows the patched version. Prefer a narrower lockfile change when the existing constraint already admits the fix. An override needs proof of compatibility for every consuming parent and an owner and removal plan. Verify changelogs and API changes, engines, peer ranges, native modules and platform-specific behavior. For risky or incompatible migrations, report the precise dependency constraint and a staged plan.

After a change, verify the same workspace and target-platform graph, reverse paths, patch provenance and relevant tests. A build with install scripts disabled may be useful for graph inspection but cannot establish that legitimate installation and runtime behavior work. Report installation and testing limits explicitly.
